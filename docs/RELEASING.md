# Releasing to npm

This repository follows Easel's tag-driven release pattern: validate the tag, run CI, build a tarball, publish it using npm trusted publishing, then create a GitHub release.

The workflow is `.github/workflows/release.yml`. Ordinary pushes to `main` do not publish anything. Keep credentials out of the repository and do not add an `NPM_TOKEN` secret for this workflow.

## One-time setup

### npm account

Use the personal npm account that should own `alpinejs-shopify-cart`. Verify its email address and enable two-factor authentication. Use Node.js 24 and a working npm CLI locally. GitHub's publishing job pins npm 12.0.2; OIDC publishing requires at least npm 11.5.1 and Node 22.14.0.

```sh
npm login --registry=https://registry.npmjs.org/
npm whoami --registry=https://registry.npmjs.org/
```

Do not paste passwords, access tokens, or recovery codes into an issue, commit, or chat.

### Bootstrap a new package

npm requires a package to exist before its trusted publisher can be configured. A brand-new package cannot use staged publishing to bypass this requirement either.

If the name is still unregistered, publish the current **0.1.0** implementation once under the non-default **bootstrap** dist-tag. This is a real public publish: it establishes package ownership and leaves an installable bootstrap version on npm. It does not publish 1.0.0 or intentionally set the `latest` tag.

From a clean checkout of `main`, while `package.json` still says `0.1.0`:

```sh
git switch main
git pull --ff-only
npm ci
npx playwright install chromium firefox webkit
npm pack --dry-run
npm publish --access public --tag bootstrap --registry=https://registry.npmjs.org/
```

`prepublishOnly` runs the full package test suite and rebuilds `dist/`. Complete npm's browser/2FA prompts. Do not add `--provenance` to this local bootstrap publish: provenance is generated by the later GitHub Actions publish.

Verify ownership and the bootstrap version:

```sh
npm owner ls alpinejs-shopify-cart --registry=https://registry.npmjs.org/
npm view alpinejs-shopify-cart@0.1.0 version --registry=https://registry.npmjs.org/
npm view alpinejs-shopify-cart dist-tags --json --registry=https://registry.npmjs.org/
```

If the package already exists, do not repeat this step or try to overwrite an existing version. Confirm that your npm account has publish access. A registry 404 does not guarantee that npm will accept a particular name at first publication.

If you do not want a bootstrap version, you can publish 1.0.0 locally instead. In that case the first version will not have this workflow's provenance, and you must not trigger a workflow that attempts to publish 1.0.0 again. Use trusted publishing for the next version. The remaining instructions assume the bootstrap route so 1.0.0 itself is published by Actions.

### GitHub environment

In repository **Settings → Environments**, create an environment named exactly **npm**:

https://github.com/BillyNoyes/alpinejs-shopify-cart/settings/environments

- Add BillyNoyes as a required reviewer.
- Leave **Prevent self-review** disabled if Billy is the only release approver.
- Under deployment branches and tags, select **Selected branches and tags**.
- Add a **tag** rule matching `v*`.

This follows Easel's release environment and puts an approval gate in front of npm publication. There are no npm secrets to add to it.

### npm trusted publisher

On npmjs.com, open the package's **Settings → Trusted publishing** and add a **GitHub Actions** publisher:

| Setting | Exact value |
| --- | --- |
| Organization or user | `BillyNoyes` |
| Repository | `alpinejs-shopify-cart` |
| Workflow filename | `release.yml` |
| Environment | `npm` |
| Allowed action | Enable direct **npm publish** |

The workflow filename is just `release.yml`, not `.github/workflows/release.yml`. Values must match exactly, including case. New configurations can default to staged publishing, so explicitly permit **npm publish** for this workflow.

Alternatively, npm's trust CLI is available in npm 11.15.0 or newer. This command uses the same pinned version as the workflow without requiring a global npm upgrade:

```sh
npx --yes npm@12.0.2 trust github alpinejs-shopify-cart \
  --repo BillyNoyes/alpinejs-shopify-cart \
  --file release.yml \
  --environment npm \
  --allow-publish \
  --registry=https://registry.npmjs.org/
```

Complete 2FA and verify the saved configuration:

```sh
npx --yes npm@12.0.2 trust list alpinejs-shopify-cart --json --registry=https://registry.npmjs.org/
```

Configure the publisher through either the website or CLI, not both. Once the trusted path is configured and verified, use the package's **Publishing access → Require two-factor authentication and disallow tokens** setting. Browser-authenticated manual publishes and trusted OIDC publishing do not require a long-lived automation token.

## Prepare 1.0.0

Do this only after the bootstrap and trust setup above are complete. Start from a clean `main` checkout.

Prepare the package README for the release as well: remove the unpublished/development notice, add `npm install alpinejs alpinejs-shopify-cart`, show the package-name import, and use the version-pinned CDN filename shown below. The npm tarball includes the README at publication time; updating the repository afterward does not replace that immutable version's packaged README. Keep the website's availability claims unchanged until the registry confirms publication.

```sh
git switch main
git pull --ff-only
npm version 1.0.0 --no-git-tag-version
npm test
npm --prefix site ci
npm --prefix site run check
git add package.json package-lock.json dist README.md
git commit -m "Prepare 1.0.0 release"
git push origin main
```

The explicit version command updates both package files without creating a tag prematurely. `npm test` rebuilds the committed distributions with matching version banners. Wait for the pushed commit's CI checks to pass before proceeding.

## Trigger publication

This tag push starts the release workflow and can result in public npm publication after approval:

```sh
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
```

Open the [Release workflow](https://github.com/BillyNoyes/alpinejs-shopify-cart/actions/workflows/release.yml). After validation, CI, and packaging finish, approve the pending **npm** environment deployment. The workflow publishes the prepared tarball with provenance under `latest`, then creates the GitHub release.

The workflow enforces:

- The package name, public registry, and repository match the trusted publisher.
- The version matches `package-lock.json` and the `v` tag exactly.
- The tagged commit is an ancestor of `origin/main`.
- CI and generated-file checks pass.
- Build and dependency scripts run in jobs without npm publishing permission.
- Only the publish job has `id-token: write`; it publishes the built artifact with lifecycle scripts disabled.

Stable versions publish to `latest`. Numbered `alpha`, `beta`, and `rc` versions publish to matching dist-tags and create prerelease GitHub releases.

## Verify publication

```sh
npm view alpinejs-shopify-cart@1.0.0 version dist.integrity dist.attestations --json --registry=https://registry.npmjs.org/
npm view alpinejs-shopify-cart dist-tags --json --registry=https://registry.npmjs.org/
gh release view v1.0.0 --repo BillyNoyes/alpinejs-shopify-cart
```

Check that `latest` is `1.0.0` and inspect the provenance shown by npm. Only after successful publication, update the website installation instructions and release-status text to use the published package and version-pinned CDN file:

```sh
npm install alpinejs alpinejs-shopify-cart
```

CDN artifact: `https://cdn.jsdelivr.net/npm/alpinejs-shopify-cart@1.0.0/dist/alpinejs-shopify-cart.min.js`.

Do not advertise that URL as available before publication. CDN propagation can lag the npm registry.

Optionally remove the bootstrap dist-tag after 1.0.0 is verified:

```sh
npm dist-tag rm alpinejs-shopify-cart bootstrap --registry=https://registry.npmjs.org/
```

This removes the tag, not the bootstrap version. Never unpublish the package merely to remove the bootstrap tag.

## Future releases and recovery

For future versions, repeat the version bump, checks, commit, and matching tag push. No additional bootstrap publish is needed.

- Do not publish the same package name and version twice; npm versions are immutable.
- If authentication fails, check the exact owner, repository, workflow filename, environment, and direct-publish permission first.
- Manual dispatch must select an existing `v` tag that matches the package; dispatching from `main` intentionally fails validation.
- If npm publication succeeded but GitHub release creation failed, re-run **failed jobs only**. Do not republish the tarball or move the tag.
- Never force-move a release tag to change code after publication. Correct it in a new version.
